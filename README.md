# 消息补获

**群聊场景下的 LLM 消息防抖插件**

> 让"@机器人 + 补充说明"不再落空，让 AI 一次性看懂用户真正想说什么。

---

## 🤔 为什么需要它

在**私聊**里，防抖是很自然的事：用户发来消息，稍等一下看有没有补充，有就一起处理，没有就正常请求 LLM。请求途中用户又发消息，也能打断重新请求。私聊只有一个用户，怎么处理都不影响别人。

但**群聊**就棘手得多：

- 每条消息都请求 LLM 太吵、太费 token；
- 只有 **@机器人 / 提及机器人**才会唤醒，其它消息一律沉默；
- 群友是**平等**的，A 和 B 各自唤醒一次，就必须分开走两轮 LLM——否则拿谁当事件主题？算谁的好感度？这次回复落在谁头上？

于是出现了这样的经典翻车现场：

```
用户A：@机器人 问你一个问题
用户A：今天天气怎么样
```

「今天天气怎么样」这条**没有 @、没有提及**，根本不会唤醒机器人。
被唤醒的只有第一条「问你一个问题」，LLM 看到的就是一个没头没尾的问题。

而第二条要等到**下一次唤醒**才能被处理——下一次是什么时候？不知道。
**消息直接落空，体验断崖式下跌。**

---

## ✨ 本插件怎么解决

一句话：**在唤醒后、请求 LLM 之前，等一小会儿，把这段时间里多出来的新消息一起补进去。**

```
用户A：@机器人 问你一个问题
插件：识别「接下来可能有补充」，自动等待 2 秒
用户A：今天天气怎么样        ← 期间发来的消息被收集
插件：把补充消息拼进上下文，正常请求 LLM
```

LLM 拿到的就是「问你一个问题 + 今天天气怎么样」的完整上下文，一次回答到位。

触发自动等待的条件（可在配置中调整）：

- 唤醒文本匹配**自动触发正则**（如「问个事」「在吗」「帮我看看」、结尾的语气词、省略号等）；
- 消息**只有一个 @机器人**、没有其它内容（"只艾特触发等待"）。

此外，所有唤醒默认都会收集**从接收到消息到请求 LLM 之间多出来的消息**（可关闭），不触发等待也不会漏。

---

## 🧩 边界情况怎么处理

这是插件真正用心的地方。

### 场景一：等待期间，**同一个用户**又 @ 了机器人

```
用户A：@机器人 问题一
（等待中）
用户A：@机器人 问题二        ← 又唤醒一次
```

- **处理方式**：新的唤醒事件**直接终止**，消息交给等待机制收集。
- **效果**：同一个用户、两次唤醒，只走**一轮 LLM**，上下文不割裂，效率和体验双赢。
- 若开启「同用户循环等待」，还可以继续开新一轮等待，把连续刷屏的补充也一网打尽（有最大时长兜底）。

### 场景二：等待期间，**另一个用户**唤醒了机器人

```
用户A：@机器人 问题一
（等待中）
用户B：@机器人 另一个问题      ← 不同用户唤醒
```

- **处理方式**：标记新的唤醒，**立即终止**当前等待，不再拖时间。
- **效果**：用户 A 的消息正常走本轮 LLM，用户 B 的消息正常排下一轮。
- **公平性不打折**：两个用户各自独立处理，谁也不占谁的坑。

### 场景三：等待期间，用户做了操作、发了消息

- 已经**发送过消息**、或已经被**终止 / 禁止请求 LLM** 的事件，不会重复收集；
- 被本插件主动 stop 的事件，会按预期被补获机制收进来，而不是被丢弃。

一句话总结：**同用户合并，异用户分流，落空消息补上。**

## 🛠️ LLM 工具：`wait_new_messages`

除了自动触发，插件还提供一个 **LLM 可主动调用的工具**，让模型自己决定"再等等看"。

适用场景：群聊里，群友 @ 了机器人但问题还没问完，或只问"在吗"，接下来可能还有补充。

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `seconds` | number | 等待秒数，通常 2 秒，**0~8 秒**，默认按配置 |
| `scope` | string | 收集范围：`user` 只收当前用户（默认）、`all` 收本群所有人、留空按插件配置 |

返回：等待期间收集到的消息文本（含时间、昵称、内容），没有则返回提示语。

> 为防止滥用，**每个事件最多调用 2 次**该工具。

## ⚙️ 配置说明

| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| **自动触发正则列表** | 一组中文常用触发词 | 唤醒文本匹配其中任意一条（`re.search` 部分匹配）即自动等待 |
| **只艾特触发等待** | `true` | 消息只有一个 @机器人、无其它内容时也自动等待 |
| **自动等待秒数** | `2.0` | 自动等待时长，**建议 2 秒**，过长会明显拖慢回复 |
| **未触发规则也收集** | `true` | 任何唤醒都收集「接收 → 请求 LLM」之间的多余消息 |
| **收集时间差** | `1.0` | 开启上项时，两者间隔超过该秒数才收集，避免无谓开销 |
| **自动收集范围** | `发送者本人` | 只收集触发者的消息，还是群里所有人的消息 |
| **等待提示语** | 见下 | 补话的开头/末尾提示，支持 `{等待时间}`、`{消息数量}` 占位符，留空则不加 |
| **最大缓存条数** | `60` | 每个会话最多缓存多少条未唤醒消息，超出丢最旧的 |
| **同用户循环等待** | `true` | 等待期间同一用户再次唤醒，是否继续开新等待 |
| **循环等待最大时间** | `60` | 连续循环等待的总时长上限，`-1` 为无限 |

**等待提示语**默认值：

- 开头语：`[自动触发等待{等待时间}秒，期间收到{消息数量}条新消息，按时间顺序：]`
- 末尾语：`<system_reminder>以上是等待期间群友发来的新消息，请与用户的原消息合并理解。</system_reminder>`

## 📦 安装与使用

1. 将插件放入 AstrBot 的插件目录，重启加载；
2. 在 WebUI / 配置文件中按需调整上方参数；
3. 群聊中正常 @ 机器人对话即可，插件会在后台自动完成防抖。

---

## 💡 设计取舍

本插件不是要复刻私聊那种"完美防抖"，而是要在**群聊的多用户公平性**约束下做到体验最优：

- 不合并不同用户的事件，避免"抢主题、抢 ID"的问题；
- 同一用户的连续唤醒合并成一轮，减少 token 与等待；
- 等待有明确上限，任何情况下都不会把消息无限拖住；
- 未被收集的事件仍会走框架原本的流程，不会"被吞掉"。

从体验上，已经比"@了机器人、又发了消息、却没人回答我"要好上一个大台阶。
