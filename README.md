消息补获
在群聊场景AI聊天中，遇到一个非常棘手的问题，在群聊中，每个用户是平等的，也就是说，如果用户A唤醒了llm，用户B又唤醒了llm，那么这两次唤醒就必须分两轮进行，而不能合为一起，否则，拿谁当此次事件的主题请求llm，插件该取谁的ID判断好感度，此次事件落在谁头上，难道新唤醒的就一定在次一个，旧唤醒的就一定当主吗，或者反之，这显然影响了公平性，群聊不同于私聊，私聊只有一个用户，如果llm请求期间，用户又发来看消息，可以立刻打断，然后把AI已发送，用户发来的消息继续请求llm，而且私聊可以防抖，在用户发来了消息之后，故意等待两秒看有没有新消息，有就一起收集没有就继续请求llm，请求llm途中发来新消息也可以立刻打断然后发起新的请求，但是群聊就很棘手了，群聊不能每条消息都请求llm，只有提及机器人名字或艾特机器人的时候才可以，否则群聊消息多，机器人每条都请求llm回复，无疑是特别吵闹且消耗token的，但是，怎么打造一个，用户发来了消息，但是接下来又有补充消息的场景呢，而且还不能影响其他用户的公平性，本插件就设计出来了：

用户A：@机器人 问你一个问题
用户A：今天天气怎么样

现状，“今天天气怎么样”那条消息，没有艾特，没有提及，根本不会唤醒，而且，唤醒的是第一条消息，请求llm时，也只有第一条消息，第二条消息要等下次唤醒llm，下次是什么时候，不知道，消息直接落空，体验直接下降

本插件：

用户A：@机器人 问你一个问题
插件：识别：接下来可能有话，等待两秒，收集新消息
收集完：正常请求llm

这听起来很简单，但是有很多边界问题，

问题1：用户A在等待期间又艾特唤醒了机器人怎么办
问题2：用户A在等待期间有用户B唤醒了机器人怎么办

插件处理方式：

如果等待期间，是同一个用户唤醒机器人，那么新的唤醒事件直接终止，由等待补获机制收集消息，同一个用户，两次艾特，两次唤醒，只走一轮llm，llm回复处理同一个用户的消息，不割裂，效率高

如果等待期间，有另一个用户唤醒了机器人怎么办，那么新的唤醒会被标记，等待直接终止，因为此新唤醒是不同用户，llm需要分别处理，而等待期间，另一个用户的唤醒了直接停止等待，不拖延时长，旧用户的消息继续正常走llm，新用户消息正常等下一轮llm

这虽然不如私聊那么完美，但是这也非常好的解决了消息防抖（用户短时间连续唤醒机器人），问的问题没有及时发出，用户唤醒后，问题稍后才补充
但是，从体验上，已经上升了一个档次了，用户再也不用，艾特了机器人，又发了消息，傻傻的困惑怎么没有解答我的问题
